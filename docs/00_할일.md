## 1. `results_shown`의 `empty=true` 오계측 수정

- [ ] `App.tsx`의 `results_shown` 가드에 studios 카탈로그 도착 여부를 추가한다

**증상.** 대시보드의 "빈손 비율"이 실제보다 10배 넘게 부풀려진다. 2026-09-02 기준 최근 7일 PostHog 데이터에서 결과 화면을 본 380명 중 176명(46%)이 빈손을 본 것으로 잡히지만, 실제로 조건 때문에 결과를 못 본 사람은 **16명(4.2%)**이다.

**원인.** `src/web/src/App.tsx`에서 두 fetch가 독립적으로 도는데 `loading` 상태는 한쪽만 추적한다.

- 슬롯 조회(`App.tsx:169` 근처) — `loading`으로 추적됨
- studios 카탈로그 조회(`App.tsx:118` 근처) — **추적되지 않음**

`hydrateSlots`(`App.tsx:433`)가 슬롯을 studios 카탈로그와 조인하는데, 카탈로그가 아직 도착하지 않으면 조인에서 슬롯이 전부 탈락한다. 그 결과 날짜 그룹은 만들어지지만(`date_group_count=1`) 그 안의 합주실이 0이 되어 `totalStudios === 0`이 되고, `results_shown`이 `empty: true`로 찍힌다. `App.tsx:473`의 가드가 `if (loading) return;` 하나뿐이라 이 순간을 막지 못한다.

**근거 (PostHog, 2026-08-26 ~ 09-02).**

| 확인한 것 | 값 |
| --- | --- |
| `empty=true` 234건 중 `filter_changes=0` | 210건 (90%) |
| `empty=true` 발생 시점 `ms_since_open` 중앙값 | 1,114ms |
| `empty=true`의 `date_group_count` | 208건이 `1` (그룹은 있는데 합주실만 0) |
| 빈손 → 다음 `results_shown`까지 걸린 시간 중앙값 | 525ms |
| 첫 화면이 빈손이던 161세션 중 조건을 바꾸지 않고 결과를 본 세션 | 135세션 |

사용자가 조건을 건드리지 않았는데 0.5초 뒤 결과가 나타난다. 즉 사용자 행동이 아니라 화면이 채워지는 도중의 중간 상태다.

**수정안.**

```ts
const [studiosLoaded, setStudiosLoaded] = useState(false);

// App.tsx:118 근처
  .then((r) => setStudios(r.studios))
  .catch(() => setStudios([]))
  .finally(() => setStudiosLoaded(true));   // 실패해도 true

// App.tsx:473
  if (loading || !studiosLoaded) return;
```

`.catch` 경로에서도 `studiosLoaded`를 세워야 한다. 그러지 않으면 카탈로그 조회가 실패했을 때 `results_shown`이 영영 발생하지 않아 퍼널 전체가 비게 된다.

**검증.** 배포 후 `empty=true` 이벤트 중 `filter_changes=0`인 비율이 90%에서 크게 떨어지는지 확인한다. 조회 방법은 [계측 조회](04_개발/06_계측_조회.md) 참고.

**주의.** 이미 쌓인 데이터는 되돌릴 수 없다. 수정 이전 구간을 볼 때는 `empty = true AND filter_changes > 0`으로 걸러야 실제 값이 나온다.

## 2. PostHog 대시보드 구성

- [ ] 대시보드 `합주실 현황` 타일 구성 (진행 중, 수작업)
- [ ] 구성 후 공개 링크(`Share → Share publicly`)를 켜서 비개발자에게 전달

계정 공유는 필요 없다. 조직 `Lunartown`의 `team_members`는 Unlimited라 초대가 무료지만, `role_based_access_control`이 현재 플랜에 없어 초대한 멤버를 읽기 전용으로 묶을 수 없다. 따라서 **읽기만 필요한 사람에게는 공개 링크가 낫다.**

타일 후보와 설정값은 세션 기록에 정리해 두었다. 핵심 3개는 다음과 같다.

- 「예약까지 가는 비율」 — Funnel: `app_open → results_shown → booking_click`, Unique users, Conversion window 1일
- 「빈손 비율 %」 — Trends 수식 모드: A(`results_shown` where `empty=true`) / B(`results_shown`) × 100. **1번 항목을 고치기 전에는 A에 `filter_changes > 0`을 함께 걸어야 한다**
- 「유입 소스별 예약 전환율」 — Funnel `app_open → booking_click`, Breakdown `utm_source`

Property value 집계에 P75가 없다(Average / Sum / Min / Max / Median / P90 / P95 / P99만 제공). Web Vitals의 공식 기준인 p75가 필요하면 HogQL로 직접 조회한다.
