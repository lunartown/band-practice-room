> 작성일: 2026-06-27

> 업데이트: 2026-07-05: 빈자리 알림 구현 완료, 후속 운영 과제 중심으로 갱신

## 1. 현재 기준

MVP의 핵심 검색 흐름은 구현·배포되어 있다. 사용자는 지역, 날짜, 시간, 인원, 합주실 조건으로 빈 시간을 찾고, 선호 합주실은 여러 곳 선택할 수 있다. 선택한 합주실은 결과가 없어도 날짜 섹션 안에 "빈 시간 없음" row로 유지되어, 사용자가 선택한 곳이 목록에서 사라진 것인지 실제로 빈 시간이 없는 것인지 확인할 수 있다.

이미 구현된 흐름:

- 합주실 검색은 결과 검색이 아니라 "합주실 선택" 진입점이다.
- 사용자는 여러 선호 합주실을 함께 고를 수 있다.
- 선택한 합주실은 자동으로 목록 위로 끌어올리지 않고, 사용자가 보던 리스트 위치와 체크 상태를 유지한다.
- 다시 검색 화면을 열었을 때 최근 선택 섹션으로 이전 맥락을 회복할 수 있다.
- 선택한 합주실 필터는 상단 개별 칩으로 노출하고, 각 칩에서 바로 해제할 수 있다.
- 선택한 합주실 중 현재 조건에 빈 시간이 없는 곳은 결과 영역에 별도 row로 남긴다.
- 즐겨찾기, 공유, 최근 선택, 당겨서 새로고침, 네이티브 푸시 알림, 내 알림 관리 화면이 붙어 있다.

## 2. 빈자리 알림 구현 현황

이전 문서에서 "다음 큰 목표"로 잡았던 빈자리 알림은 현재 1차 구현이 완료되었다.

### 2.1 프론트 UX

- 빈 시간 없음 row와 날짜별 빈 상태에서 "알림" CTA를 제공한다.
- 알림 등록 전 확인 시트에서 날짜, 시간대, 합주실/지역, 인원, 최소 연속 시간을 요약한다.
- 앱에서 푸시 권한과 토큰을 확보한 뒤 서버 디바이스 등록을 수행한다.
- 메뉴의 "내 알림" 화면에서 구독 목록을 조회하고 삭제할 수 있다.
- 알림 수정은 서버 PATCH 없이 "새 구독 생성 → 기존 구독 삭제" 순서로 처리한다. 생성 실패 시 기존 구독이 보존되도록 하기 위해서다.
- 알림을 탭하면 해당 날짜·합주실 조건의 결과 화면으로 이동한다. 앱을 보는 중 포그라운드 알림을 받으면 슬롯을 갱신한다.

### 2.2 API·DB

현재 알림 API는 `/api/v1/notifications` 아래에 있다.

```txt
POST   /api/v1/notifications/devices
POST   /api/v1/notifications/subscriptions
GET    /api/v1/notifications/subscriptions?installId=...
DELETE /api/v1/notifications/subscriptions/:id
```

초기 초안의 `/api/v1/alerts` 경로는 쓰지 않는다. 로그인은 없고, 앱이 생성해 보관하는 `installId`를 익명 사용자 식별자로 쓴다. FCM 토큰은 회전될 수 있으므로 디바이스의 갱신 가능한 속성으로 취급한다.

DB에는 다음 계층이 구현되어 있다.

- `devices` — 설치 ID, FCM 토큰, 플랫폼, 앱 버전, 마지막 확인 시각
- `notification_subscriptions` — studio/area 대상, 날짜, 시간대, 최소 시간, 인원 조건
- `slot_available_events` — 슬롯이 가용으로 바뀐 이벤트 큐
- `notification_deliveries` — 발송 로그와 중복 발송 방지 키

### 2.3 발송 경로

슬롯이 새로 `AVAILABLE` 상태가 되면 DB 트리거가 `slot_available_events`에 이벤트를 쌓는다. 별도 dispatcher가 미처리 이벤트를 구독 조건과 매칭하고 FCM으로 보낸 뒤 처리 완료를 표시한다. 같은 구독에 같은 방·날짜·시작 시각을 두 번 보내지 않도록 발송 로그에 유니크 제약을 둔다.

Android는 HIGH 채널과 전용 상태바 아이콘을 사용한다. iOS/Android 모두 네이티브 앱(Capacitor) 안에서 푸시 경로를 탄다.

## 3. 당겨서 새로고침 구현 현황과 후속

현재 `POST /api/v1/slots/refresh`는 pull-to-refresh에서 넘어온 합주실 ID를 받되, 서버 보호를 위해 실제 수집은 오래된 소스 우선 최대 `MANUAL_MAX_SOURCES`개만 동기 실행한다. 초과분은 `skipped.reason = capped`로 응답하며, 지금 단계에서는 자동으로 이어 수집하지 않는다.

현재 동작:

- payload 상한: `MANUAL_MAX_REQUEST_STUDIO_IDS` 기본 200
- 실제 수집 상한: `MANUAL_MAX_SOURCES` 기본 6
- 전역 동시성: `MANUAL_SCRAPE_CONCURRENCY` 기본 2
- 신선도 스킵: `MANUAL_FRESH_MINUTES` 기본 10분
- 수동 갱신 쿨다운: `MANUAL_COOLDOWN_MINUTES` 기본 5분
- 응답은 `refreshed`, `skipped(fresh/cooldown/capped)`, `failed`로 나뉜다.

이 방식은 전체 결과 화면에서 대량 요청이 실패하던 문제를 막는 단기 해법이다. 다만 HTTP 요청 안에서 수집을 끝내는 구조라 모바일 네트워크 끊김, 앱 백그라운드 전환, Render 무료 리소스 제한에 취약하다.

### 목표 상태

- pull-to-refresh는 "즉시 모든 합주실을 최신화"가 아니라 "오래된 합주실 확인 작업을 요청"하는 동작으로 정의한다.
- 서버는 오래된 소스부터 제한된 동시성으로 천천히 처리한다.
- 사용자는 기존 결과를 계속 보면서 "확인 중", "일부 확인 완료", "실패" 같은 진행 상태만 낮은 위계로 본다.
- 앱 재시작·연결 끊김 후에도 작업 상태를 다시 조회할 수 있어야 한다.

### 구현 후보

1. `refresh_jobs`, `refresh_job_items` 테이블을 추가하거나 기존 `scrape_jobs` 재사용 가능성을 검토한다.
2. `POST /api/v1/slots/refresh-jobs`는 요청을 저장하고 `jobId`를 즉시 반환한다.
3. 워커는 `refresh_job_items`를 오래된 순으로 집어 `MANUAL_SCRAPE_CONCURRENCY` 안에서 처리한다.
4. `GET /api/v1/slots/refresh-jobs/:id`로 현재 상태를 조회한다.
5. 진행 상태 표시는 1차로 polling을 붙이고, 필요하면 `GET /api/v1/slots/refresh-jobs/:id/events` SSE를 추가한다.
6. 프론트는 완료 이벤트마다 전체 슬롯을 즉시 다시 긁기보다 2~5초 단위로 debounce해서 재조회한다.

## 4. 다음 구현 후보

우선순위는 알림 신규 개발이 아니라 운영 안정화와 관측성 개선에 둔다.

| 순서 | 작업 | 이유 |
| --- | --- | --- |
| 1 | 알림 발송 요약/실패 로그 관측성 강화 | 실제 푸시 누락·중복·토큰 오류를 빠르게 확인해야 함 |
| 2 | 만료·과거 날짜 구독 정리 상태 점검 | 오래된 구독이 쌓이면 매칭 비용과 사용자 신뢰에 영향 |
| 3 | 당겨서 새로고침 작업화 | 모바일 요청 시간과 Render 리소스 한계를 줄여야 함 |
| 4 | 관리자 화면에서 매핑·이미지·비활성 처리 UX 보강 | 운영자가 깨진 예약 링크나 썸네일을 빠르게 고쳐야 함 |
| 5 | 프론트 결과 로딩/갱신 상태 미세 조정 | 새로고침과 알림 탭 이동 후 사용자가 상태를 더 명확히 이해해야 함 |

## 5. 열어둘 질문

- 알림 만료 기준을 단순히 날짜 경과로 둘지, 발송 성공 후 구독을 자동 소진할지?
- 한 구독에 여러 날짜가 있을 때 일부 날짜만 발송된 경우 UI에서 어떻게 표시할지?
- refresh job을 기존 `scrape_jobs`와 합칠지, 사용자 요청 진행률 때문에 별도 테이블로 둘지?
- FCM 실패 코드별로 토큰 비활성화 정책을 얼마나 공격적으로 가져갈지?
- 사용자에게 수집 신선도/실패 상태를 어느 정도까지 노출할지?

## 6. 하지 않을 것

- "카탈로그에 없는 합주실"에 대한 알림은 만들지 않는다. 먼저 합주실 검색에서 카탈로그 존재 여부를 확인하게 한다.
- 전체 지역/전체 합주실에 대한 과도하게 넓은 푸시 알림을 기본 CTA로 밀지 않는다.
- 알림을 예약 보장처럼 표현하지 않는다. 최종 예약은 원본 예약 페이지에서 확정된다.
- `scrapedAt` 같은 내부 수집 메타를 사용자에게 신선도 점수처럼 노출하지 않는다.
