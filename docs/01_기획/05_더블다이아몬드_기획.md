# 더블다이아몬드 기획

> 작성일: 2026-07-08
> 상태: 초안
> 목적: MVP 배포 이후 운영·반복 개선 단계에서 무엇을 더 검증하고 좁힐지 정리한다.

## 0. 결론

현재 제품의 핵심 선택은 유지한다.

> 합주실은 합주실 정보 포털이 아니라 **예약 가능 시간 검색 엔진**이다.

다음 기획의 초점은 새 메뉴를 넓히는 것이 아니라, 사용자가 실제 예약 결정을 내리는 흐름을 더 짧고 믿을 수 있게 만드는 것이다.

우선순위:

1. 사용자가 지역·날짜·시간 조건을 빠르게 정하고 결과를 확인한다.
2. 선호 합주실이 없을 때도 "빈 시간 없음" 상태와 다음 행동이 분명하다.
3. 빈자리 알림이 재방문과 예약 후보 전환으로 이어지는지 검증한다.
4. 데이터 정확도와 수집 실패는 사용자에게 떠넘기지 않고 내부 운영 지표로 관리한다.

## 1. 더블다이아몬드 적용 방식

이 문서는 초기 아이디어 발산용이 아니라, 이미 배포된 MVP를 기준으로 다음 개선 범위를 정하기 위한 프레임이다.

| 단계 | 질문 | 산출물 |
| --- | --- | --- |
| Discover | 사용자는 어떤 상황에서 합주실을 찾고 어디서 막히는가? | 관찰 가설, 사용자 상황, 검증해야 할 미확인 사실 |
| Define | 우리가 지금 가장 먼저 풀 문제는 무엇인가? | 핵심 사용자, 문제 문장, 성공 기준, 제외 범위 |
| Develop | 어떤 해결책 후보가 있는가? | 해결 방향, 후보 기능, 실험 계획 |
| Deliver | 무엇을 먼저 출시·측정할 것인가? | 우선순위, 릴리스 범위, 지표, 의사결정 기준 |

## 2. Discover: 문제 넓게 보기

### 2.1 관찰된 사용자 상황

기존 문서와 현재 제품 방향을 기준으로 보면 사용자는 대체로 다음 상황에서 서비스를 쓴다.

| 상황 | 사용자의 목표 | 기존 방식의 불편 |
| --- | --- | --- |
| 오늘·내일 급하게 찾기 | 지금 가능한 방을 빠르게 찾고 예약 페이지로 이동 | 여러 예약 플랫폼에서 날짜와 시간을 반복 선택 |
| 2~4주 뒤 정기 합주 잡기 | 가능한 날짜·시간 후보를 여러 개 뽑아 공유 | 오늘/내일 중심 탐색으로는 범위가 좁음 |
| 선호 합주실 확인 | 늘 가던 곳이 비었는지 먼저 확인 | 선호 합주실이 없을 때 대안 탐색과 대기 행동이 끊김 |
| 대안 예약 후 대기 | 대안은 잡았지만 선호 합주실이 열리면 옮기고 싶음 | 다시 직접 확인해야 하며 잊기 쉬움 |

### 2.2 사용자의 실제 판단 순서

사용자는 합주실 소개를 읽기보다 다음 질문에 답하려 한다.

1. 이 지역에서 가능한가?
2. 원하는 날짜에 가능한가?
3. 원하는 시간대와 최소 이용 시간에 맞는가?
4. 가격이 받아들일 만한가?
5. 선호 합주실이 없다면 대안을 잡을 것인가, 알림을 걸 것인가?
6. 원본 예약 페이지에서 실제로 확정할 수 있는가?

따라서 화면의 정보 위계는 업체 소개, 사진, 장비 설명보다 날짜·시간·가격·예약 이동이 앞서야 한다.

### 2.3 현재 강점

- 네이버 예약과 스페이스클라우드처럼 흩어진 예약 가능 시간을 한곳에서 보여준다.
- 최소 30일 범위 탐색이라는 차별점이 있다.
- 지역 선택, 날짜 섹션 중심 결과, 선호 합주실 선택 흐름이 제품 본질과 맞다.
- 최종 예약을 외부로 넘기는 한계를 인정하고 내부 탐색 속도에 집중한다.
- 빈자리 알림으로 "없음" 상태 이후의 행동을 만들 수 있다.

### 2.4 아직 모르는 것

아래 항목은 문서상의 가설이며, 실제 사용 데이터나 인터뷰로 확인해야 한다.

| 미확인 사실 | 왜 중요한가 | 확인 방법 |
| --- | --- | --- |
| 사용자는 급한 예약과 정기 예약 중 어느 상황에서 더 자주 쓰는가? | 기본 날짜·시간 UX 우선순위가 달라진다 | 이벤트 로그, 5명 내외 사용자 인터뷰 |
| 첫 진입에서 지역 선택이 충분히 빠른가? | 오픈 화면이 도움이 되는지 판단한다 | 지역 선택률, 선택까지 걸린 시간 |
| 결과가 없을 때 사용자가 조건을 완화하는가, 이탈하는가? | 빈 상태 CTA의 방향을 정한다 | 빈 결과 노출 후 행동 로그 |
| 선호 합주실 알림을 실제로 등록하는가? | 알림 기능의 제품 가치를 판단한다 | 알림 CTA 노출 대비 등록률 |
| 알림을 받은 뒤 다시 예약 페이지로 이동하는가? | 알림이 재방문 기능인지, 단순 보조 기능인지 판단한다 | 푸시 오픈률, 알림 진입 후 예약 클릭률 |
| 데이터 불일치 경험이 얼마나 자주 생기는가? | 수집 주기·운영 우선순위를 정한다 | 제보, 원본 이동 직후 이탈 패턴, 내부 수집 실패율 |

## 3. Define: 핵심 문제 좁히기

### 3.1 핵심 사용자

가장 먼저 만족시킬 사용자는 다음이다.

> 서울권에서 모바일로 합주 일정을 조율하고, 선호 지역이나 선호 합주실 안에서 가능한 시간대를 빠르게 확정하려는 밴드 멤버.

보조 사용자는 다음이다.

- 정기적으로 같은 지역·합주실을 예약하는 사용자
- 몇 주 뒤 후보 일정을 찾는 사용자
- 선호 합주실이 찰 경우 대안을 예약하고 빈자리 알림을 기다리는 사용자

### 3.2 문제 문장

사용자는 합주 날짜와 대략적인 지역이 정해져도, 합주실별 예약 채널이 흩어져 있어 가능한 방을 비교하는 데 시간이 걸린다. 특히 선호 합주실이 없을 때는 대안을 찾고, 나중에 빈자리가 나는지 확인하는 흐름이 끊긴다.

우리는 사용자가 모바일에서 몇 번의 조건 선택만으로 예약 가능한 시간대를 비교하고, 원하는 곳이 없으면 알림까지 걸 수 있게 해야 한다.

### 3.3 제품 원칙

| 원칙 | 설명 |
| --- | --- |
| 빈 시간이 먼저다 | 업체 소개보다 날짜·시간·방·가격·예약 이동이 먼저 보인다 |
| 조건 변경은 즉시다 | 사용자가 조건을 바꿀 때마다 기다리는 경험을 만들지 않는다 |
| 없음도 결과다 | 선호 합주실이 비어 있지 않으면 목록에서 사라지는 대신 빈 상태와 다음 행동을 보여준다 |
| 최종 예약은 원본에서 한다 | 직접 예약·결제보다 원본 예약 페이지 이동 전 비교 가치를 키운다 |
| 신선도는 내부 책임이다 | 사용자가 stale 여부를 판단하게 하지 않고 수집·운영으로 흡수한다 |

### 3.4 성공 기준

정성 기준:

- 사용자가 설명을 읽지 않아도 지역·날짜·시간을 바꿔 결과를 볼 수 있다.
- 결과가 없을 때 "다음에 무엇을 할지"가 자연스럽다.
- 선호 합주실이 꽉 찬 상황에서도 서비스가 쓸모 있다.
- 원본 예약 페이지로 이동하기 전 여러 후보를 비교했다는 느낌이 든다.

정량 후보:

| 지표 | 의미 |
| --- | --- |
| 첫 지역 선택률 | 첫 화면이 탐색을 시작시키는지 |
| 조건 변경 후 결과 조회율 | 필터가 사용자의 의도와 맞는지 |
| 원본 예약 클릭률 | 검색 결과가 실제 예약 후보로 이어지는지 |
| 빈 결과 후 조건 완화율 | 빈 상태가 사용자를 붙잡는지 |
| 알림 CTA 등록률 | 없음 상태 이후의 행동이 설득력 있는지 |
| 알림 오픈 후 원본 클릭률 | 알림이 재방문과 예약 후보 전환에 기여하는지 |
| 7일·30일 재방문율 | 정기 예약 도구로 자리 잡는지 |

### 3.5 제외 범위

다음은 이번 문제 정의의 해결책에서 제외한다.

- 직접 예약·결제
- 커뮤니티, 게시판, 악보, 밴드 활동 가이드
- 공연장 예약 전체 기능
- 개인연습실 상품 검색
- 네이버 지도와 경쟁하는 업체 소개 상세 페이지
- 사용자 화면의 신선도·stale 표시

## 4. Develop: 해결책 넓게 만들기

### 4.1 해결 방향

| 방향 | 핵심 아이디어 | 기대 효과 |
| --- | --- | --- |
| 빠른 조건 설정 | 지역 진입, 최근 조건 복원, 날짜·시간 칩 | 첫 탐색 시간을 줄인다 |
| 촘촘한 결과 비교 | 날짜 섹션 중심 리스트, 가격·시간·방 정보 밀도 유지 | 여러 후보를 빠르게 비교한다 |
| 선호 합주실 중심 | 선택한 합주실 유지, 빈 시간 없음 row | "내가 보려던 곳"의 상태를 놓치지 않는다 |
| 없음 이후 행동 | 빈자리 알림, 조건 완화, 대안 탐색 | 빈 결과가 곧 이탈이 되지 않게 한다 |
| 운영 신뢰도 | 수집 실패율, 갱신 지연, 소스별 오류 모니터링 | 사용자가 느끼기 전 내부에서 문제를 잡는다 |

### 4.2 후보 기능

| 후보 | 우선순위 | 이유 |
| --- | --- | --- |
| 검색 퍼널 이벤트 계측 | Must | 현재 제품이 어디서 막히는지 알아야 다음 결정을 할 수 있다 |
| 원본 예약 클릭 이벤트 계측 | Must | 내부 검색이 실제 예약 후보로 이어지는지 확인해야 한다 |
| 빈 결과·빈 row 행동 계측 | Must | 알림과 조건 완화 중 무엇이 효과적인지 판단한다 |
| 알림 등록·오픈·예약 클릭 퍼널 | Must | 빈자리 알림의 제품 가치를 검증한다 |
| 최근 조건 복원 품질 개선 | Should | 반복 사용자의 재진입 마찰을 줄인다 |
| 조건 공유 URL 개선 | Should | 단톡방 합주 일정 조율과 맞다 |
| 지역·합주실 추천 정렬 | Could | 데이터가 쌓인 뒤 개인화 없이도 탐색을 줄일 수 있다 |
| 업체 상세 정보 확장 | Won't | 네이버 지도 대비 차별점이 약하고 유지보수 비용이 크다 |

### 4.3 실험안

| 실험 | 가설 | 판단 기준 |
| --- | --- | --- |
| 빈 row에 알림 CTA를 명확히 노출 | 선호 합주실이 없을 때 사용자는 대안을 찾는 동시에 알림을 걸고 싶다 | 빈 row 노출 대비 알림 등록률 |
| 결과 없음 화면에 조건 완화와 알림을 함께 제공 | 전체 결과가 없을 때 이탈보다 조건 변경 또는 알림 등록이 늘어난다 | 빈 결과 후 이탈률 감소 |
| 원본 예약 버튼 문구 비교 | "예약하기"보다 원본 플랫폼 이동이 분명한 문구가 신뢰를 높인다 | 원본 클릭률, 뒤로 돌아오는 비율 |
| 최근 조건 자동 복원 | 반복 사용자는 이전 지역·시간 조건에서 다시 시작하길 원한다 | 재방문 후 첫 행동까지 시간 감소 |
| 공유 URL 문구 정리 | 단톡방 공유 시 조건이 분명하면 후보 논의가 빨라진다 | 공유 클릭 후 조건 유지율 |

## 5. Deliver: 먼저 좁혀 출시·측정하기

### 5.1 다음 릴리스의 제품 목표

다음 릴리스의 목표는 기능을 크게 늘리는 것이 아니라, 현재 핵심 흐름을 측정 가능한 상태로 만드는 것이다.

> 사용자가 지역·날짜·시간 조건으로 결과를 확인하고, 선호 합주실이 없으면 알림을 등록하거나 조건을 완화한 뒤, 원본 예약 페이지로 이동하는 흐름을 계측한다.

### 5.2 1차 범위

포함:

- 검색 진입, 지역 선택, 날짜·시간 변경, 합주실 선택 이벤트
- 결과 있음·없음·선호 합주실 빈 row 노출 이벤트
- 원본 예약 클릭 이벤트
- 알림 CTA 노출, 등록, 해지, 푸시 오픈, 오픈 후 원본 클릭 이벤트
- 내부 운영용 수집 성공률·실패율·소스별 오류 요약

제외:

- 직접 예약·결제
- 사용자 계정 기반 예약 이력
- 개인화 추천
- 업체 상세 페이지 확장
- 사용자 화면의 수집 신선도 표시

### 5.3 의사결정 기준

| 관찰 결과 | 다음 결정 |
| --- | --- |
| 첫 지역 선택률이 낮다 | 오픈 화면 문구·지역 배열·최근 조건 복원을 먼저 개선한다 |
| 조건 변경은 많지만 원본 클릭이 낮다 | 결과 정렬, 가격 표시, 시간 묶음 표현을 개선한다 |
| 빈 결과 후 이탈이 높다 | 조건 완화 CTA와 알림 CTA의 위치를 조정한다 |
| 알림 등록은 높지만 오픈 후 클릭이 낮다 | 알림 문구, 딥링크, 알림 조건 정확도를 개선한다 |
| 알림 등록 자체가 낮다 | 알림보다 선호 합주실 비교·대안 탐색을 우선한다 |
| 수집 실패율이 높다 | UI 개선보다 소스 안정화와 재수집 전략을 우선한다 |
| 특정 지역 검색이 많은데 결과가 부족하다 | 새 합주실·소스 추가를 우선한다 |

### 5.4 단계별 실행안

| 순서 | 작업 | 산출물 |
| --- | --- | --- |
| 1 | 핵심 퍼널 이벤트 정의 | 이벤트명, 속성, 개인정보 제외 기준 |
| 2 | 검색·결과·원본 클릭 계측 | 실제 탐색 퍼널 |
| 3 | 알림 퍼널 계측 | 등록부터 푸시 오픈 후 행동까지의 흐름 |
| 4 | 운영 지표 정리 | 수집 성공률, 실패 소스, 오래된 데이터 내부 대시보드 |
| 5 | 1~2주 데이터 리뷰 | 다음 제품 개선 우선순위 결정 |
