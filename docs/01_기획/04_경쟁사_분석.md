## 2. 비교 기준

- 예약 가능한 시간대를 얼마나 빨리 찾을 수 있는가
- 모바일에서 핵심 행동까지 얼마나 적은 방해가 있는가
- 조건 변경 시 결과가 즉시 바뀌는가

- 부가 기능이 핵심 탐색을 방해하지 않는가
- **사용자가 서비스를 어떻게 발견하는가** (2026-08-30 추가)

## 3. 밴드룸 재조사 (2026-08-30)

### 3.1 현황

- 도메인 `band-room.com`. Next.js SSR.
- 운영 주체는 개인 사업자(대표 신동휘, 경기 남양주). 통신판매업 신고 완료.
- iOS·Android 앱 출시. `Band Room` v1.0.4 (2026-08-18), 카테고리 '유틸리티', 한국어 전용, 리뷰·평점 0건.
- 서울 12개 권역. 검색 대상 합주실 85개, 정보 페이지 137개, 개인연습실 61개. 서울 근교(부천·부평·수원·분당·인천·일산)는 전부 "준비중".
- 메뉴: 빈 시간 검색 / 합주실 정보 / 공연 / 공연장 정보 / 공연장 예약현황 / 공지사항 / 개인 연습실 / 악기점·리페어샵 / 악보검색 / 밴드 활동 가이드 / 게시판(합주실 예약양도·연합공연 팀구인·팀원 구인·동아리원 모집) / 내 계정.

### 3.2 핵심 구조 — 온디맨드 스크래핑

밴드룸은 사용자가 검색할 때 원본 예약 페이지를 실시간으로 조회한다. 로딩 화면에 "공간별 예약 페이지를 확인하는 중입니다"라고 표시된다.

그 결과 검색 화면에 다음 제약이 상시 노출된다.

> 서버 안정화를 위해 검색량 제한이 적용됩니다. 현재 날짜 1개 기준 합주실 최대 5개 선택 가능

직접 측정한 값(합정/홍대, 합주실 5개, 룸 28개, 1일치):

| 구간 | 소요 |
| --- | --- |
| 첫 결과 표시 | 약 16초 |
| 전체 결과 완료 | 약 30초 |
| 합정/홍대 23개 전부 확인 | 5회 검색 ≈ 2분 30초 |

이 제약은 기능 선택이 아니라 아키텍처의 결과다. 사전 적재로 바꾸지 않는 한 풀리지 않고, 사전 적재로 바꾸면 "실시간 조회"라는 자체 마케팅 문구를 버려야 한다.

### 3.3 검색 플로우

3단계 위저드다. **날짜(최대 3개) → 지역(12개 권역) → 합주실(최대 5개)** 를 고른 뒤 검색 버튼을 누르고 결과를 기다린다. 조건 하나를 바꾸려면 단계를 되돌아가 다시 대기해야 한다.

앱도 같은 위저드를 그대로 쓴다. 하단 탭은 `검색 / 합주실 / 내밴드 / 공연 / 더보기` 5개다.

### 3.4 결과 화면 — 우리보다 나은 부분

룸 단위로 한 행씩 쌓고, 각 행에 **0~23시 눈금 위 초록 막대로 빈 구간을 그린다.** 룸별 시간당 가격을 함께 적고, 행마다 원본 예약 페이지로 가는 버튼을 둔다. 검색 결과를 통째로 공유하는 "링크 복사"가 있다.

언제·얼마나·연속으로 비었는지가 한 화면에서 읽힌다. 우리 결과 카드는 `15~22시` 같은 범위 칩 하나라 **중간 공백을 표현하지 못한다.**

합주실 정보 페이지에는 가격·인원·장비 필터가 있다.

### 3.5 운영 기준 문서에서 드러난 계획

`/methodology`("운영 기준", 최종 정리 2026-05-23)에 데이터 범주를 4개로 공개해 두었고, 그중 둘은 아직 서비스에 없다.

| 범주 | 내용 | 상태 |
| --- | --- | --- |
| 검색·예약 판단 | 합주실 빈 시간, 상세, 개인연습실, 공연장 | 운영 중 |
| 밴드관리 | 공지, 밴드 일정, 일정 조율, 선곡회의, 피드백/자료룸 | 앱에 일부 |
| 공연·홍보 | 공연 준비 보드, 홍보/티켓, QR 티켓, 결제 | 계획 |
| **입점·운영** | **입점 신청, 운영 합주실, 예약 링크, 운영 도구, 가격/방 정보** | **계획** |

같은 문서에 "광고, 추천, 입점 노출은 사용자가 일반 검색 결과로 오해하지 않도록 별도 표시한다", "코드가 존재하더라도 운영 정책에 맞지 않으면 배포 화면에서 링크를 제거할 수 있다"는 문장이 있다. 전자는 수익모델, 후자는 만들어두고 못 내보낸 기능이 있다는 뜻이다.

**네 번째 범주(입점)만 성격이 다르다.** 나머지 확장은 화면을 늘릴 뿐이지만, 입점은 합주실 사업자와의 관계를 만든다. 성사되면 저쪽은 데이터를 긁는 대신 공급받게 되고, 우리가 스크래핑으로 확보한 데이터 우위의 근거가 약해진다. 다만 이는 코드가 아니라 영업이라 확장을 벌여둔 상태에서 실행될지는 미지수다. 실제 구현 진척은 3.8 참고 — 입점 도구는 아직 404다.

### 3.7 실제 해자 — 커뮤니티·오프라인 유통

**밴드룸의 가장 큰 강점은 제품도 SEO도 아니라 유통이다.**

이 항목은 브라우저 조사로 관측되지 않는다. 운영자 관찰로 확인한 내용이며 앞 항목들과 근거의 성격이 다르다.

- 운영자가 실제로 밴드 커뮤니티를 운영한다. 서비스 이전에 사람이 먼저 있다.
- 카카오톡 단체방과 인스타그램 계정을 함께 운영하고, 새 소식이 그 멤버들을 통해 즉시 퍼진다.
- 합주실 현장에 광고 포스터를 걸고, 대학 게시판·뮬 같은 밴드 커뮤니티 사이트·각종 밴드 단톡방에 실시간으로 확산시킨다.

즉 저쪽의 광고는 매체 구매가 아니라 **인맥을 통한 노출**이다. 비용이 거의 들지 않고, 닿는 사람이 정확히 타깃이며, 전달자의 신뢰가 함께 얹힌다. 우리가 인스타·페이스북에 돈을 태워 얻는 유입과 질이 다르다.

합주실 예약은 밴드 단위로 움직이고 밴드는 이미 단톡방과 커뮤니티에 묶여 있다. 한 명에게 닿으면 팀 전체가 따라온다. 이 구조에서는 제품 완성도나 검색 노출의 열세가 상당 부분 상쇄된다.

**우리에게는 이에 대응하는 유통 경로가 없다.** 현재 유입은 유료 광고와 직접 방문뿐이고 광고를 끄면 사라진다. 검색 유입이 0인 것보다 이쪽이 더 근본적인 격차다. 검색은 만들 수 있지만 커뮤니티는 시간이 든다.

### 3.8 미출시 기능 진척 (robots.txt 라우트 정찰, 2026-08-30)

`band-room.com/robots.txt`의 `Disallow` 목록에 미공개 라우트가 그대로 노출돼 있어, 각 경로의 HTTP 상태와 페이지 성격만 확인했다(로그인 시도·데이터 조회 없이 상태 코드와 셸 여부만).

| 경로 | 상태 | 정체 |
| --- | --- | --- |
| `/bands` | 200 | 로그인 벽 (밴드 관리) |
| `/band-schedule` | 200 | 로그인 벽 (밴드 일정) |
| `/schedule` | 200 | 로그인 벽 (일정) |
| `/setlist-meeting` | 200 | 로그인 벽 (선곡 회의) |
| `/auth` `/community` `/pamphlet-design` `/partner-venue-admin` `/show-prep` | 404 | 서버에 존재하지 않음 |

200으로 뜬 4개는 전부 홈과 동일한 빈 SPA 셸(11568B, 같은 title)이다. 서버는 누구에게나 같은 셸을 주고 로그인 판단은 클라이언트 JS가 한다. 받은 것은 "로그인하세요" 화면일 뿐 실제 밴드 데이터가 아니다.

**해석:** 저쪽의 실제 구현 진척은 로그인 뒤 밴드 관리 기능(밴드/일정/선곡회의)까지다. 반면 수익과 직결되는 **입점 도구(`/partner-venue-admin`), 포스터 제작(`/pamphlet-design`), 커뮤니티(`/community`)는 404 — URL만 선점하고 아직 만들지 않았다.** `/methodology`가 계획 문서인 것과 일치한다.

즉 **입점 모델은 문서·URL 예약까지 갔을 뿐 구현 전이다.** 공급자(합주실) 확보 경쟁에서 우리가 이미 뒤처진 것이 아니라, 양쪽 다 아직 시작 전이다. 이 점은 3.7의 커뮤니티 격차와 달리 시간 여유가 있는 축이다.

## 5. 유입 — 우리가 지고 있는 지점

제품 지표는 우리가 앞서지만 **발견 경로가 없다.**

PostHog 2026-07-13~08-30, `app_open` 405회 기준:

| 유입 | 횟수 |
| --- | --- |
| 직접 | 290 |
| 인스타그램 | 68 |
| 페이스북 | 41 |
| 구글 | 3 |
| 빙 | 3 |
| AI 엔진(chatgpt·perplexity 등) | 0 |

GA4 최근 28일: 전체 190세션 중 Organic Search 7세션, Paid Social 68, Direct 71.

7주간 검색 유입 6회다. 주별 추이를 보면 8/23 주에 광고를 집행해 200 opens / 109명이 찍혔고 앞뒤 주는 18~36이다. **광고를 켜면 오고 끄면 사라지는 구조다.**

원인은 두 겹이다.

1. **색인할 페이지가 없다.** sitemap URL이 1개고, 그 1개도 본문 없는 SPA 셸(2.5KB)이다. "합정 합주실", "강남 합주실 가격" 같은 검색어에 대응할 페이지가 존재하지 않는다.
2. **크롤러가 볼 내용이 없다.** LLM 크롤러(GPTBot, PerplexityBot, ClaudeBot)는 대부분 JS를 실행하지 않는다. 241개 합주실 데이터를 보유하고도 기계가 읽을 수 없는 형태로 두고 있다. AEO 유입 0건은 이 결과다.

밴드룸은 합주실별·지역별 SSR 페이지와 `/about`, `/methodology`까지 232개 URL을 색인 가능한 상태로 두고 있다. 실제로 "합주실 예약" 계열 검색에서 `band-room.com`이 결과에 노출되는 것을 확인했다(한국 구글 기준 순위는 미확인).

다만 저쪽의 유입이 전부 검색에서 오는 것도 아니다. 실제 동력은 3.7의 커뮤니티·오프라인 유통이고, 검색은 그 위에 얹힌 층이다. 우리는 두 층이 모두 비어 있다.

부가로, 우리 서비스명 "합주실"은 일반명사라 브랜드 검색이 카테고리 검색과 구분되지 않는다. 재방문과 입소문이 이름에서 새는 구조다.

## 6. 네이버 예약/지도 대비

네이버 예약과 네이버 지도는 업체 단위 정보와 예약 확정에 강하다. 우리가 같은 방식으로 업체 정보 페이지를 만들면 불리하다.

- 업체 정보는 네이버가 더 정확할 가능성이 높다
- 위치, 전화, 리뷰, 길찾기, 사진은 네이버 지도에 이미 있다
- 우리 쪽 정보가 틀리면 신뢰도 손상이 크다

따라서 차별화는 정보량이 아니라 **여러 업체의 빈 시간대를 한 번에 비교하는 속도**에서 나와야 한다.

## 7. 차별화 가설

### 가설 1. 정보 포털이 아니라 합주실 검색 엔진이어야 한다

합주실 소개, 공연 정보, 공연장 예약, 개인연습실, 커뮤니티보다 "조건에 맞는 합주실 빈 시간"을 먼저 보여준다.

### 가설 2. 외부 이동은 인정하고, 내부 탐색을 압도적으로 빠르게 만든다

최종 예약은 네이버 예약 등 외부로 이동한다. 대신 사용자가 외부로 가기 전 후보를 고르는 과정은 네이버를 여러 번 여는 것보다 훨씬 빨라야 한다.

### 가설 3. 조건 변경은 서버 왕복 없이 즉시 반영되어야 한다

백엔드는 예약 가능 데이터를 주기적으로 사전 적재한다. 프론트는 필요한 범위의 데이터를 먼저 받고, 시간/지역/합주실 필터는 클라이언트에서 즉시 처리한다.

밴드룸의 5개 제한과 30초 대기가 이 가설의 반대 사례다.

### 가설 4. 데이터 정확도는 제품이 보장하고 사용자에게 떠넘기지 않는다

신선도를 사용자에게 보여주는 것이 아니라, 제품이 자주 갱신해 정확도를 내부적으로 보장한다 (의사결정 로그 2026-06-21).

### 가설 5. 빠른 제품이라도 발견되지 않으면 비교당할 기회조차 없다 (2026-08-30 추가)

제품 우위는 사용자가 도달한 뒤에만 작동한다. 색인 가능한 페이지가 없으면 검색과 AI 답변 양쪽에서 후보에 들지 못한다.

## 8. 배울 점

- **커뮤니티·오프라인 유통(3.7).** 가장 큰 격차이고 가장 따라잡기 어렵다. 광고비로 대체되지 않는다.
- **룸별 24시간 타임라인.** 결과의 시간 정보 밀도에서 밴드룸이 우리보다 낫다. 범위 칩으로는 중간 공백을 못 보여준다.
- **결과에 룸별 시간당 가격 병기.** 비교·정렬 축으로 쓰인다.
- **가격·인원·장비 필터.** 우리 `rooms.capacity` 커버리지는 485개 중 151개(31%)라 인원 필터를 걸 수 없다. 데이터 보강이 선행 과제다.
- **SEO 구조.** 합주실별·지역별 정적 페이지가 검색 유입의 실체다.
- **검색 조건이 담긴 링크 공유.** 우리 공유는 합주실 단위다.
- **지도 기반 탐색.**
- **수익 경로를 먼저 세운 것.** 통신판매업 신고, 입점, 광고 노출 표기 원칙까지 문서로 정리해 두었다. 우리 우위는 제품 우위지 사업 우위가 아니다.

## 9. 피해야 할 것

- 첫 화면에 긴 안내문이나 공지 모달을 두는 것
- 조건 변경마다 사용자를 기다리게 하는 것
- 비교 대상 수를 제품이 제한하는 것
- 사이드바에 부가 메뉴를 과도하게 늘려 핵심을 흐리는 것
- 네이버 지도보다 못한 정보 페이지를 만드는 것
- 공연/커뮤니티/가이드 등으로 초점을 흐리는 것
- 단위가 틀린 카피("합주실 28개"인데 실제로는 룸 28개)

## 10. 앞으로 지켜볼 신호

밴드룸의 기능 추가 자체는 추적 가치가 낮다. 다음 두 가지만 본다.

1. **입점 공지가 실제로 뜨는지.** 합주실 사업자 확보는 제품 품질과 무관하게 진행되며, 성사되면 데이터 우위 구도가 바뀐다.
2. **우리 자연 검색·AI 유입이 0에서 벗어나는지.** 현재 유입 구조가 광고 의존이라 이 지표가 사업 지속성과 직결된다.

3. **저쪽 커뮤니티 채널의 활동량.** 카톡방·인스타·오프라인 포스터가 계속 도는지가 저쪽 성장의 실제 동력이다. 기능 추가보다 이쪽이 선행 지표다.

반대로 검색 속도, 커버리지, 소요시간 조건에서 밴드룸이 우리를 따라잡을 가능성은 낮다. 아키텍처를 바꿔야 하고, 그 과정에서 자체 마케팅 문구를 부정해야 하기 때문이다.
