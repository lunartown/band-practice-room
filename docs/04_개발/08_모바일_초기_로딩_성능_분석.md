# 모바일 초기 로딩 성능 분석

분석일: 2026-09-08  
대상: `https://hapjusil.com/` 첫 방문  
근거 추적 파일: `Trace-20260908T085022.json.gz`

## 결론

모바일 초기 로딩 저하는 실제 성능 회귀다. 방문자 구성이나 PostHog 대시보드의 표시 방식만으로 설명되지 않는다.

이번 추적에서 최종 LCP는 **8,961ms**였다. 결과 데이터가 6,258ms에 도착한 뒤 첫 결과 전체를 한꺼번에 렌더링했고, 이어서 PostHog 세션 리플레이가 약 42,000개 DOM 노드를 초기 스냅샷으로 처리하면서 메인 스레드를 1,934ms 동안 점유했다. 결과 렌더링과 동시에 대표 이미지도 대량으로 요청되어 페이지의 네트워크 작업은 최대 74초까지 이어졌다.

한 가지 원인만 제거해서 끝나는 문제가 아니다. 다음 세 요인이 연결되어 있다.

1. 첫 진입에서 전국 예약 슬롯 5,234개를 가져온다.
2. 받은 결과를 한꺼번에 렌더링해 DOM 노드 약 42,450개와 이벤트 리스너 약 3,424개가 생긴다.
3. 거대한 DOM을 PostHog가 녹화하고, 화면 밖 대표 이미지까지 동시에 요청한다.

가장 먼저 **첫 화면 결과를 점진적으로 렌더링**해야 한다. 이는 DOM 크기, 이미지 요청 수, PostHog 초기 스냅샷 비용을 함께 줄인다. 즉시 적용할 수 있는 완화책은 PostHog 세션 녹화 시작을 첫 결과 표시 이후 유휴 시점으로 늦추는 것이다. 그다음 슬롯 API 응답 구조를 축소해 결과가 도착하는 시점 자체를 앞당겨야 한다.

## 병목별 근거

### 1. 첫 결과가 도착하기 전 데이터 비용

기본 필터는 오늘 날짜, 전체 지역, 최소 2명이다. 이 조건의 슬롯 API는 슬롯 **5,234개**를 반환하며 응답 크기는 다음과 같다.

| API | 소요 시간 | 압축 전 크기 |
| --- | ---: | ---: |
| `/api/v1/areas` | 594ms | 약 1KB |
| `/api/v1/studios` | 3,043ms | 약 498KB |
| `/api/v1/slots?dates=2026-09-08&minCapacity=2` | 3,616ms | 약 1,546KB |

각 슬롯에는 `date`, 시작·종료 시각, 상태, 가격, 수집 시각, 합주실·방 ID와 예약 URL이 반복된다. 특히 같은 방의 예약 URL과 수집 시각이 슬롯마다 반복되어 전송량이 커진다.

슬롯 API가 완료되기 전에는 실제 결과를 렌더링할 수 없다. 따라서 LCP를 안정적으로 2.5초 아래로 낮추려면 프런트엔드 최적화와 별개로 응답 구조 축소가 필요하다.

### 2. 과도한 초기 DOM

결과 렌더링 이후 추적에 기록된 규모는 다음과 같다.

- DOM 노드: 약 42,450개
- JavaScript 이벤트 리스너: 약 3,424개
- JavaScript 힙 사용량: 약 31MB

사용자가 처음 보는 영역 밖의 날짜·합주실·방·시간 칩까지 모두 DOM으로 만든 결과다. 렌더링 직후 305ms 작업과 다수의 style/layout 계산이 발생했다.

### 3. PostHog 세션 리플레이의 초기 스냅샷

`posthog-js`가 들어 있는 `module-BwFhwFEp.js`의 `load` 핸들러가 6,920ms에 시작해 1,934ms 동안 실행됐다. 이 구간에서 확인된 비용은 다음과 같다.

- Layout 실행: 180회
- Layout 누적 시간: 약 1,174ms
- 긴 작업 전체 시간: 1,934ms

PostHog 자체가 항상 2초를 쓰는 것이 아니라, 이번에는 녹화해야 할 초기 DOM이 약 42,000개로 커져 비용이 증폭됐다. 세션 녹화만 끄거나 늦추면 이번 추적의 LCP는 줄지만, 과도한 DOM과 이미지 문제는 남는다.

### 4. 대표 이미지 일괄 요청과 실패 폴백

결과 렌더링 직후 화면 밖 행을 포함한 대표 이미지가 한꺼번에 요청된다. 추적에서 확인한 요청 수는 다음과 같다.

| 출처 | 요청 수 | 전송량 | 마지막 완료 |
| --- | ---: | ---: | ---: |
| `hapjusil.com` 전체 | 156개 | 약 1,262KB | 16.6초 |
| `ldb-phinf.pstatic.net` | 32개 | 약 1,576KB | 63.6초 |
| `naverbooking-phinf.pstatic.net` | 6개 | 약 696KB | 73.9초 |

2026-08-30의 `FIX: 대표 썸네일 초기 로딩 누락 방지` 변경에서 네이티브 `loading="lazy"`가 제거됐다. 당시의 이미지 누락을 재발시키지 않기 위해 단순 복원은 피한다. 첫 화면의 소수 이미지는 즉시 요청하고, 나머지는 `.result-list`를 root로 둔 `IntersectionObserver`로 직접 관리하는 방식이 적합하다.

네이버 CDN의 `?type=w480` 요청이 404를 반환한 뒤 원본을 다시 요청하는 사례도 있다. 실패 순간 `IMG`의 대체 텍스트가 화면에 그려져 이번 추적의 최종 LCP 후보가 됐고, 이어서 요청한 510KB 원본은 Slow 4G에서 54초가 걸렸다. 지원하지 않는 리사이즈 형식을 호스트·URL별로 구분하거나, 실패 결과를 세션 동안 캐시해야 한다.

### 5. 초기 경로의 외부 스크립트와 폰트

주요 외부 자산은 다음과 같다.

| 자산 | 완료 시점 | 압축 전 크기 |
| --- | ---: | ---: |
| Pretendard CSS | 2,368ms | 3KB |
| Google Analytics | 6,540ms | 445KB |
| Meta Pixel 본체 | 5,475ms | 406KB |
| PostHog 추가 모듈 5개 | 최대 6,632ms | 합계 약 328KB |

Pretendard CSS는 앱 CSS의 `@import`에서 발견되어 직렬로 요청된다. Google Analytics·Meta Pixel·PostHog는 낮은 네트워크 우선순위지만 초기 구간의 대역폭과 CPU를 함께 사용한다. 이들은 핵심 원인인 데이터·DOM 문제를 해결한 뒤 유휴 로딩 대상으로 조정한다.

## 개선 순서

### 1단계: 첫 화면 점진 렌더링

첫 화면에는 현재 정렬 결과 중 10~15개 합주실만 렌더링한다. 사용자가 아래로 이동하면 다음 묶음을 추가한다. 가변 높이 행 때문에 즉시 완전한 가상화를 도입하기 어렵다면 묶음 단위 점진 렌더링으로 시작한다.

같이 적용할 항목:

- 첫 화면의 대표 이미지만 eager로 요청
- 화면 밖 이미지는 `.result-list` 기반 `IntersectionObserver`로 요청
- 스크롤 300~500px 앞에서 미리 로드
- 리사이즈 실패 여부를 세션 캐시해 동일 URL 재시도 방지

예상 효과는 DOM·리스너 수 감소, 초기 레이아웃 감소, 이미지 요청 감소, PostHog 스냅샷 비용 감소다.

### 2단계: PostHog 리플레이 시작 지연

이벤트 분석은 초기화하되 세션 리플레이는 첫 결과 paint 이후 `requestIdleCallback` 또는 제한 시간 뒤에 시작한다. 로딩 과정 리플레이가 필요하면 일부 세션만 초기부터 녹화하는 방안을 검토한다.

이 단계는 이번 추적에서 확인된 약 2초의 메인 스레드 정지를 빠르게 완화한다. 점진 렌더링과 함께 적용해야 스냅샷 비용 자체도 줄어든다.

### 3단계: 슬롯 API 응답 축소

슬롯 단위 객체 5,234개 대신 날짜·방별로 묶은 응답을 검토한다.

- `bookingUrl`, `scrapedAt`, `studioId`, `roomId` 반복 제거
- 방별 공통 필드는 한 번만 전송
- 연속 시간대를 구간으로 병합하거나 간결한 시간 배열로 표현
- 첫 화면에 필요한 요약과 방 상세 데이터를 분리하는 방안 검토

목표는 오늘 전체 지역 응답을 압축 전 300KB 이하로 줄이는 것이다.

### 4단계: 초기 외부 자산 정리

- Pretendard 자체 호스팅 또는 초기 시스템 폰트 사용
- Google Analytics·Meta Pixel을 첫 결과 이후로 지연 가능한지 검토
- 사용하지 않는 PostHog surveys·dead-clicks 모듈 로드를 설정에서 제한

## 1차 개선 측정 결과

[PR #239](https://github.com/lunartown/band-practice-room/pull/239)에서 1단계 점진 렌더링과 2단계 리플레이 지연을 적용했다. 첫 12개 합주실을 렌더링하고 실제 결과 스크롤 영역의 `IntersectionObserver`로 12개씩 추가한다. 사진도 행이 화면 근처에 올 때 생성하며, 첫 카드의 첫 사진만 `loading="eager"`와 `fetchpriority="high"`로 요청한다.

Lighthouse 모바일 기본 조건에서 운영 API의 동일 날짜·결과를 사용해 개선 전후를 교차로 3회씩 측정했다. 아래 값은 중앙값이다.

| 지표 | 개선 전 | 개선 후 | 변화 |
| --- | ---: | ---: | ---: |
| 성능 점수 | 46 | 65 | +19점 |
| 관측 LCP | 3.60초 | 2.82초 | -21.6% |
| Lantern LCP | 32.47초 | 20.66초 | -36.4% |
| TBT | 998ms | 175ms | -82.5% |
| 메인 스레드 작업 | 4.80초 | 2.35초 | -51.0% |
| DOM 요소 | 10,891개 | 689개 | -93.7% |
| 요청 수 | 223개 | 34개 | -84.8% |
| 전송량 | 73.7MB | 7.9MB | -89.3% |

초기 브라우저 추적의 LCP 8.96초와 Lighthouse 관측 LCP는 수집 방식과 네트워크 실행 조건이 달라 절대값을 직접 비교하지 않는다. 이번 표는 동일한 Lighthouse 조건의 개선 전후 상대 비교다. 운영 효과는 배포 후 PostHog 모바일 LCP p75로 다시 확인한다.

## 완료 기준

동일 조건(Slow 4G, CPU 4×)에서 최소 3회 측정하고 중앙값으로 판단한다.

| 지표 | 현재 추적 | 1차 목표 |
| --- | ---: | ---: |
| FCP | 2.68초 | 2.0초 이하 |
| LCP | 8.96초 | 4.0초 이하 |
| 첫 결과 표시 | 6.78초 | 3.5초 이하 |
| 초기 DOM 노드 | 약 42,450개 | 5,000개 이하 |
| 10초 이내 이미지 요청 | 150개 이상 | 20개 이하 |
| 200ms 초과 메인 스레드 작업 | 4건 | 0건 |

운영 지표는 대시보드의 p90과 별도로 LCP **p75**를 기준으로 본다. Core Web Vitals의 양호 기준인 2.5초 이하는 최종 목표로 두고, 1차 변경에서 회귀 이전 수준으로 얼마나 회복되는지 먼저 확인한다.

## 측정상 주의점

- DevTools CPU 제한은 실제 ARM 모바일 CPU와 동일하지 않다.
- 단일 추적은 네트워크 편차가 있으므로 API 시간의 절대값보다 요청 크기와 사건 순서를 중점적으로 본다.
- 추적의 최종 LCP 후보는 리사이즈 요청이 실패한 `IMG` 노드의 대체 텍스트다. 그래서 노드 이름은 `IMG`, 내부 이벤트는 `LargestTextPaint`로 기록됐다.
- 이 추적 파일에는 세션·URL·성능 세부 정보가 포함될 수 있으므로 저장소에는 넣지 않고 로컬 분석 근거로만 보관한다.
